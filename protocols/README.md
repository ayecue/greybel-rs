# Protocol definitions

A definition folder contains `<major>.<minor>.protocol` files. It declares a duplex protocol, its messages, and their types, or types alone. Generators use the newest minor of the selected major.

The multi-major [calculator conformance definition](../duplex/conformance/calculator/) contains [`1.0.protocol`](../duplex/conformance/calculator/1.0.protocol), [`1.1.protocol`](../duplex/conformance/calculator/1.1.protocol), and [`2.0.protocol`](../duplex/conformance/calculator/2.0.protocol). It demonstrates both minor additions and a major layout change.

| Target | Generation entry point |
|---|---|
| Rust | `include_protocol!("$DUPLEX/conformance/calculator", major = 1, role = client)` or `include_types!("$DUPLEX/conformance/calculator", major = 1)` |
| TypeScript | `duplex_ts::Module::protocol(major)` or `Module::role(major, Role::Provider)`; see the [TypeScript guide](../duplex/ts/README.md#generated-modules) |
| C# | `duplex_cs::Module::protocol(major, namespace)` or `Module::types(major, namespace)`; see the [.NET guide](../duplex/dotnet/README.md#generated-code) |

Rust macro paths are crate-relative unless a leading `$NAME/` selects an environment variable. [`greyhack/`](greyhack/) is generated by `greybel/dotnet/greyhack-util` from Grey Hack's network contracts.

## Syntax

```text
use core 1.0;
deprecated "2.0 reads keys";          // or `unsupported;`

protocol Io = "greybel-io" {
    open Credentials;                 // client handshake payload
    ack Session;                      // provider acceptance payload
    refuse Denial;                    // provider denial payload

    flavour stdio { health_check = off; }
    security authenticated;

    provider Page {                   // listens and handles these messages
        message OutputBatch { entries: list<Output> }
        message ReadKey { prompt: string } -> Result<Key, ReadFailure>
        message Count { to: u32 } -> Stream(Phase, u64)<u32>
        message Upload { name: string, chunks: Stream(_, Digest)<Chunk> } -> Receipt
    }
    client Program {}
}

const MAX_ROWS: u16 = 24;
struct PrintOptions { new_line: bool = true, replace: bool }
union Output { Print { text: string, flatten options: PrintOptions }, Clear }
union Key { Char(char), Enter, F(u8) }
enum Signal { Hang = 1, Kill = 9 }
```

Documentation comments are copied into generated code. Types, variants, members, messages, and peers use PascalCase. Fields use snake_case and become camelCase in TypeScript.

### Types and fields

- Primitive and collection types: `bool`, `char`, `string`, `bytes`, `u8`–`u64`, `i8`–`i64`, `f32`, `f64`, `fixed32`, `fixed64`, `list<T>`, and `record<T>` with string keys.
- `T?` is nullable. `name?: T` is an optional field, distinct from null. `flatten name: Struct` embeds the struct's fields in its holder.
- `fixed32` and `fixed64` are unsigned fixed-width integers. TypeScript uses `bigint` for all 64-bit integers and `Uint8Array` for bytes.
- Enum members have explicit unique values below 2³² or implicit sequential values.
- `const NAME: T = value;` declares a scalar or enum constant. Constants cannot reference other constants.
- `name: T = value` supplies a default for older peers and generated constructors. Defaults may be literals, enum members, constants, or null; compound values only allow null. A defaulted field is neither optional nor flattened.

### Requirements and limits

Types may declare requirements in parentheses:

```text
string(1..=32, match "[a-z0-9_]+")
bytes(..=256KiB)
u8(13..=120)
f64(0.0..=1.0)
list<string(..=16)>(..=8)
record<T>(1..)
```

Ranges are `least..=most`, `..=most`, or `least..`. Lengths count UTF-8 bytes, items, or entries. Requirements apply to present, non-null values and may nest. Patterns match the entire string in linear time; their compiled tables are limited to 256 KiB.

`limit 64KiB;` sets the maximum encoded size of each client-sent frame of a message. Set it on the protocol or an individual message; a message limit overrides the protocol limit. If neither declares one, the definition limit is **64 KiB**.

This definition limit is distinct from core `max_message`, which defaults to **64 MiB** and can be configured by channel options or a transport flavour. Core limit behavior is specified in [Sending and limits](../duplex/SPEC.md#sending-and-limits).

`Stream<T>(..=1000)` bounds stream item count. Requirements, limits, timeouts, and flavours affect behavior rather than binary layout.

Providers validate client traffic before reading unbounded values and reject violations as `Invalid`. Senders validate unless configured as `unvalidated`; clients do not validate provider traffic except for `max_message`.

### Messages, streams, and handshakes

- A message without `->` is a notification. `-> T` returns one value; `-> Result<T, F>` also allows a declared failure of enum or union type `F`.
- `Stream(Start, End)<Item>` has a start, items, and an end. `_` omits the start or end; `Stream<Item>` omits both. Responses may also be `Result<Stream(...)<...>, F>`.
- A message's final field may be a stream. Its other fields form that stream's start.
- `-> T timeout 5s` sets the handler timeout, or the maximum delay between stream items. Response-credit waits do not count.
- `open`, `ack`, and `refuse` declare handshake payloads. Their acceptance and denial behavior is part of [negotiation](../duplex/SPEC.md#negotiation).
- Message type ids are assigned per receiver in declaration order. Client role is 0; provider role is 1.

Stream credit, cancellation, timeout, validation, and failure behavior are defined in [Messages and streams](../duplex/SPEC.md#messages-and-streams). Rust stream writers use `send_all` to write as credit permits. TypeScript stream APIs, including `sendAll`, are documented in the [TypeScript guide](../duplex/ts/README.md#channels-and-streams).

### Tags

A tag is metadata on a definition item. Generators expose tags as metadata for conversion and routing. Declare every tag with its value type, or with no value for a flag, and the places where it may appear:

```text
/// A message's id elsewhere.
tag game_id: u32 on message;
tag list: string on field;
tag window on field;                          // a flag
tag alias: string on field, variant repeated; // more than once on one item
tag kind: Kind on struct, enum;               // a member of an enumeration

@game_id(34)
message Scan { @list("strValues") ip: string, @list("intValues") @window pid: i32 }
```

- Places are `protocol`, `message`, `field` (of a message, struct or variant), `struct`, `union`, `variant`, `enum`, and `member`. A stream takes no tags.
- A value is a literal or constant of the tag's type: a boolean, character, text, number, or member of an enumeration.
- An item takes any number of tags in the order written. A tag occurs once per item unless declared `repeated`.
- Tags and their declarations are not part of the layout, fingerprint, or migrations. They may change in any minor, released or not.

Generated code retains tags as data. See the [TypeScript tag API](../duplex/ts/README.md#tags) and [C# tag API](../duplex/dotnet/README.md#tags). Rust exposes them through `duplex_core` as follows:

| Definition item | Rust metadata |
|---|---|
| Protocol, message, struct, union, or enum | `Tagged::TAGS` |
| Fields of a message, struct, or variant | `Tagged::FIELDS`, and by name `Fields::field` → `ValueRef` |
| Variant or enum member | `ValueRef::Variant` / `Member` |

Rust also generates, per peer, an enum of handled notifications (`{Peer}Notification`) with `attach`. It presents every notification a channel receives as one value with its `name`, `tags`, and fields. The generated `{Peer}Channel` trait has a `send_{message}` method per message the peer sends. Any driver's peer channel implements it, so sending code can store a `dyn {Peer}Channel` without naming the driver type.

### Flavours and security

`flavour transport { ... }` overrides channel behavior for a named driver transport:

```text
health_check = off;
health_check = { interval = 1s, unhealthy_threshold = 2, close_threshold = 5 };
stream_window = 64;
timeout = 30s;
max_message = 4MiB;
```

Channel options take precedence over flavours, then driver and core defaults. Durations use milliseconds or `ms`, `s`, `m`; sizes use bytes or `B`, `KiB`, `MiB`, `GiB`. Health-check defaults and their algorithm are defined in [Health checks](../duplex/SPEC.md#health-checks).

`security encrypted;` or `security authenticated;` declares the required transport security. Append `signed` to require signed batches. Incompatible channels close as `Insecure`; see [Security](../duplex/SPEC.md#security).

## Versions

A minor is append-only. Every other layout change requires a new major:

| A minor may | Only a major may |
|---|---|
| Append optional or defaulted fields | Add required fields or insert fields elsewhere |
| Append enum members and union variants | Change or remove fields, variants, members, or member values |
| Append messages to either peer block | Remove or move messages; change responses, failures, or streams |
| Add types | Change types, the channel, or the core major |
| Rename items; change docs, status, constants, and flavours | Change handshake payloads or field defaults |

Layouts are positional, so renames do not alter them. `message New renames Old` explicitly pairs renamed messages for migrations. Every item records the minor that introduced it.

`fingerprints.json` freezes released layouts. Every version except the newest must be recorded. From the repository root, release pending versions with:

```sh
cd duplex/rs
RELEASE_VERSIONS=1 cargo test -p duplex-protocol
```

Peers use the client's major and the older minor. Fields introduced later are absent or defaulted; newer messages, variants, and members fail as `UnsupportedVersion`. Negotiation and migration behavior are specified in [Versions and connections](../duplex/SPEC.md#versions-and-connections).

## Migrations

Providers chain migrations between consecutive majors to upgrade incoming traffic and downgrade outgoing traffic. The calculator's two majors can be included and connected as follows:

```rust
mod v1 { duplex_core::include_protocol!("$DUPLEX/conformance/calculator", major = 1, role = provider); }
mod v2 { duplex_core::include_protocol!("$DUPLEX/conformance/calculator", major = 2, role = provider); }
duplex_core::include_migration!("$DUPLEX/conformance/calculator", from = 1, older = v1, newer = v2);
```

Generated migrations pair message segments by name and receiver. Identical layouts migrate automatically; incompatible segments require handwritten methods. Messages present in only one major fail as `UnsupportedVersion`. Handshake payloads cannot change across migrated majors.

TypeScript migration generation and channel registration are described in the [TypeScript guide](../duplex/ts/README.md#migrations).

## Binary layout and shared contract

- Fields are grouped by their introducing minor. Each block starts with flags for booleans and optional/nullable presence, followed by present values in declaration order.
- Integers use varuints, zigzagged when signed; `u8` and `i8` use one byte. Fixed-width integers and floats are little-endian. Strings, bytes, lists, and records are length-prefixed.
- Unions encode a variant index followed by its payload; enums encode the member value.
- Batch and frame layouts belong to the [core definition](../duplex/core/).

`duplex_protocol::Plan` is the shared layout contract for every generator. It resolves field blocks, flags, encodings, additions, fingerprints, and message ownership. `MigrationPlan` resolves shared message segments and automatic rewrites; `Symbol` supplies generated names.

Rust, TypeScript, and C# conformance tests read and write every fixture in [`duplex/conformance/fixtures.json`](../duplex/conformance/fixtures.json).

## Runtime and drivers

Core layouts, behavior, and executable scenarios live in [`duplex/`](../duplex/). See [`duplex/SPEC.md`](../duplex/SPEC.md) for hubs, transports, batching, security, connections, streams, limits, and backpressure.

| Transport | Rust | TypeScript |
|---|---|---|
| Worker | `duplex-driver-web` | `duplex-driver-worker` |
| Byte stream | `duplex-driver-stdio` | `duplex-driver-stdio` |
| HTTP | `duplex-driver-http` provider | `duplex-driver-http` client |
| WebSocket | `duplex-driver-websocket` provider | `duplex-driver-websocket` client |
| Memory, for peers on one thread | `duplex-driver-memory` | — |
| Tests | `duplex-test-support::Memory` | Package test drivers |

Drivers advertise `CLIENT`, `PROVIDER`, and `PERSISTENT` capabilities. Channels require a compatible driver. Protocols whose clients receive unsolicited messages require `PERSISTENT`. Driver packages document transport-specific setup and limits; TypeScript packages are indexed in the [TypeScript guide](../duplex/ts/README.md#packages).
